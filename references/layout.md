# 产出结构：每个文件是干什么的

打包结果分两部分：**安装目录**（在机器上跑的那份）与**部署包**（用来分发到其他机器的压缩件）。

```
<输出目录>/
├── <项目名>/                       安装目录：拷到目标机双击 启动.bat 即可
│   ├── server.js                   应用入口（版本号唯一来源）
│   ├── public/                     静态资源
│   ├── data/                       业务数据（空目录，永不随包分发、升级不覆盖）
│   ├── runtime/node.exe            便携运行时（--full 时才有，实现目标机零安装）
│   ├── watchdog.js                 进程守护：崩溃 2 秒后重启、日志轮转、止损
│   ├── 启动.bat                    运行时探测 → 端口检测（80 占用则提示/回退）→ 记 _port.txt → 拉起守护 → 开浏览器
│   ├── 停止.bat                    写 _stop.flag → 停守护 → 停服务 → 清标志
│   ├── 安装.bat                    解压包内的安装入口（调 setup.ps1）
│   ├── 防火墙放行.bat              管理员运行：放行入站端口 + 程序
│   ├── 开机自启.bat                切换式：放/删启动文件夹快捷方式
│   ├── setup.ps1                   安装/升级引擎（包根这一份是本次要执行的）
│   ├── tools/deploy/_setup.ps1     同一份引擎，供目标机以后接收远程升级
│   ├── version.txt                 版本 + 日期（引擎用它做版本比对）
│   ├── 安装说明.txt                给现场看的说明（端口/防火墙/升级/日志位置）
│   ├── _port.txt                   运行期生成：实际使用的端口
│   ├── _stop.flag                  运行期生成：停止信号
│   ├── _watchdog.pid               运行期生成：守护进程 PID
│   └── server.log                  运行期生成：服务日志（>5MB 轮转为 .1）
└── 部署包/
    ├── <项目名>_升级包_v<版本>_<日期>.zip        常规包：解压后双击 安装.bat
    └── <项目名>_一键升级_v<版本>_<日期>.bat      单文件自解压：zip 以 base64 内嵌，双击即装
```

## 安装引擎（`setup.ps1`）做了什么

这是整个包里最值钱的部分，也是踩坑最多的部分。

| 步骤 | 行为 | 关键设计 |
|---|---|---|
| ① 定位安装目录 | 注册表记录 → 包内目录 → 常见位置扫描（打分制）→ 弹框手选 | 临时目录（`%TEMP%`）里的路径一律不作候选，否则会把包自己当安装目录，`Copy-Item` 报 "with itself" |
| ② 检查现状 | 旧版本号、运行时、端口占用、数据文件大小 | 顺带 `-DryRun` 预演出口 |
| ③ 备份 | 现有入口与静态目录 → `_升级备份_<时间戳>/` | 只留最近 3 份，避免堆满磁盘 |
| ④ 停服务 | 按端口定位 PID，不全局 `taskkill node.exe` | 端口从 `_port.txt` / `-Port` 解析，避免误杀与"升级后版本没变" |
| ⑤ 覆盖 | 入口文件直接覆盖；静态目录先拷成 `.<new>` 再原子改名 | 拷一半失败也不会把站点搞成半残 |
| ⑤·补 钩子 | 可选：`tools/deploy/post-upgrade.js` | 幂等迁移（新增配置/字典），失败不影响升级 |
| ⑥ 重启 | 优先经 `_run_hidden.vbs` 拉守护进程 | 直接拉 `node server.js` 会丢掉启动脚本里设的端口 |
| ⑦ 校验 | 轮询 `/api/version` 比对版本 | 版本一致才算成功；不一致要提示而不是当成成功 |
| 失败回滚 | 还原入口与静态目录，并重启旧版本 | 远程无人值守升级的最后一道保险 |
| 收尾 | 注册表记安装位置、写升级日志、清理旧备份 | 下次升级可全自动定位 |

**自派机制（不显眼但关键）**：引擎被"服务进程"拉起时，Windows 会连坐——服务进程被杀，它 spawn 的子进程约 1 秒后一起消失，升级会永远卡在"停止服务"那一步。所以引擎第一步就把自己重新派生成独立进程，原进程立刻退出交棒。

## 为什么数据目录不进包

三条理由，缺一条都会出事：

1. 升级是覆盖代码，**不能**顺带把用户数据换成开发机的那份
2. 包会通过网络/优盘流转，带真实业务数据等于泄漏（签名、客户信息、内部记录）
3. 大小与可审计性：包越小越容易分发；包里有什么一目了然

构建脚本的自检会拒绝任何 `data/` 条目——这是硬红线，不要为提高"开箱即用度"绕过它。需要预置数据就走「升级后钩子」或后台导入。

## 版本号为什么只留一个来源

```
入口文件 APP_VERSION  →  version.txt（构建时写入）  →  /api/version（运行时返回）  →  引擎校验
```

四处引用同一个值，任何一处手改都会造成"版本看上去对、实际不对"。所以：

- 构建脚本**只读** `APP_VERSION`，不写
- 文件名里的版本去掉前导 `v`（`v1.2.0` → `_v1.2.0_`），但 `version.txt` 保留原样，因为引擎要用它和 `/api/version` 做**等值比较**
